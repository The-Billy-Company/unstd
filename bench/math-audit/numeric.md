# Numeric and iterator backend audit

Audit date: 2026-10-22 America/Los_Angeles. Production files were read without modification. No dependencies were installed. The full per-callable inventory is `numeric-inventory.json`; benchmark source, exact measured-source copy/hash, raw samples and correctness observations are in this directory. `numeric-provenance.json` maps the measured source to the maintained driver; run `probe_numeric.py --verify-only` for untimed checks or pass `--output /tmp/math-numeric-rerun.json` for a new timing run. Absence of a proposed swap means that no swap meeting semantic and no-regression constraints was established, not that all alternatives have been exhaustively proven slower.

## Observed stack and routes

The existing interpreter reports Python 3.13.16 on macOS ARM64; packages are NumPy 2.5.3, SoundFile 0.14.0, libsndfile 1.2.2, whenever 0.10.5, immutables 0.21 and sortedcontainers 2.4.0. `immutables.Map.__module__ == 'immutables._map'` confirms the installed C implementation. SoundFile loads the bundled `.venv/lib/python3.13/site-packages/_soundfile_data/libsndfile_arm64.dylib`. These observations are host-specific; lock versions do not prove deployed runtime versions.

`audio.read`, `blocks`, `write`, and `Writer` prefer SoundFile when present. NumPy+wave and pure-stdlib array+wave are fallback tiers. Therefore the measured fallback decoder improvement below does **not** accelerate the currently selected SoundFile path. Pack arrays already use NumPy; scalar packing is a direct stdlib alias. Clocks, container classes, `batched`, `pairwise`, and `flatten` also use direct backend aliases, without dispatch wrappers.

## Security finding requiring build provenance

The loaded libsndfile version is the version identified by [the CVE Program record for CVE-2026-88386](https://raw.githubusercontent.com/CVEProject/cvelistV5/main/cves/2026/88xxx/CVE-2026-88386.json). The MITRE record describes misaligned writes while parsing crafted WAV format chunks and a resulting denial of service. Its CISA assessment is medium 5.5, availability impact, with no confidentiality/integrity impact. [The upstream report](https://github.com/libsndfile/libsndfile/issues/1150) describes failure on strict-alignment or sanitizer builds; [the official memcpy fix](https://github.com/libsndfile/libsndfile/commit/474e4d328b1e6240b93ec6ed14efb7c6a44bee57) closed it September 1, 2026. The installed version/path alone cannot establish whether a vendor backported this fix, and host exploitability was **not** tested or proven. No malicious native fixture was executed.

The actionable security step is to verify the exact bundled binary's source revision/patch provenance and use a maintained build containing that fix. Retain the SoundFile API to avoid Python wrapper overhead. The native patch itself has not been benchmarked here, so no throughput/no-overhead claim is made for it. Merely raising the Python SoundFile floor cannot prove that a patched libsndfile is loaded: SoundFile [documents bundled-before-system loading](https://python-soundfile.readthedocs.io/en/latest/), and its [0.14.0 release notes](https://github.com/bastibe/python-soundfile/releases/tag/0.14.0) separately describe a concurrent-open race fix.

## Measured candidates

Seven paired alternating rounds measured wall and thread CPU time, with GC disabled only within batches, on an ordinary host. Inputs were constructed outside timers. Ratios below are median paired baseline/candidate CPU, so values above one favor the candidate. Results are warm measurements; the OS and hardware were not isolated, and these are neither confidence intervals nor a deployment guarantee.

| Candidate | Tiny input | 1,024 samples | 262,144 samples | Verdict |
|---|---:|---:|---:|---|
| PCM16 to int16: reshape raw view then **owned copy**, kernel | 10.62x (1 sample); 10.25x (16) | 13.06x | 48.17x | Promising fallback-only simplification |
| Same, complete BytesIO wave parse + decode | 2.23x (1); 2.12x (16) | 2.54x | 13.34x | Candidate for a future change after full route checks |
| Direct float32 cast + in-place power-of-two scaling, full read | 0.92x (1); 0.96x (16) | 1.13x | 1.51x | Reject blanket swap: tiny-case regression |
| Direct float64 cast + in-place scaling, full read | 0.94x (1); 1.03x (16) | 1.05x | 1.21x | Tiny/noisy cases fail no-regression requirement |
| Pack Python float list using existing portable struct helper | 1.33x (1); 2.10x (16) | 3.21x | 2.58x | Existing explicit API is useful for suitable callers |
| Same struct alternative for ndarray input | 0.35x (1); 0.18x (16) | 0.009x | 0.002x | Severe regression: retain ndarray NumPy route |

For int16 full reads all seven measured paired CPU ratios remained above one (1-sample 2.06–2.50x; largest 11.84–14.49x). This is good local evidence, not proof for other Python builds, architectures, empty-file workloads, multichannel timings, or concurrent consumers.

Correctness probes compared the baseline and prototype byte-for-byte, including dtype, shape, writability, and `OWNDATA`: all 256 PCM8 codes, all 65,536 PCM16 codes, and 100,020 seeded/boundary PCM32 codes, requested float32/float64/int16, 1/2/4 channels, empty buffers, partial sample/channel frames, and unsupported widths. The PCM16/int16 shortcut returns `arr.copy()` after reshape: independent owned writable storage; dtype remains `<i2`, exactly matching baseline and native on this ARM64 host. It does not accidentally return a read-only bytes-backed view. Float-write ties/NaNs/infinities, native SoundFile parsing, 24-bit decode, and full public streaming lifetimes were not altered or claimed verified by this prototype.

Portable struct packing is not a safe automatic replacement: NumPy truncates float-to-integer conversions and accepts additional dtypes/shapes, while struct requires integer-compatible values and its portable subset. Applying a Python-list shortcut to all supported inputs would change accepted inputs, failure behavior, array/subclass behavior, or add a per-call dispatcher. `unpack_array` already returns a zero-copy NumPy view; fresh-list portable decoding was 38x slower at 1,024 elements and roughly 1,000x slower at the largest shape, with different ownership and type semantics. Keep both existing explicit contracts.

## Operations and boundaries

Audio math is fixed-point sample scaling by `2**(bits-1)`, unsigned PCM8 centering, clipping to signed rails, nearest rounding on fallback writes, channel reshape, and RIFF header size/byte-rate products. Buffer frame alignment, ragged channel validation, integer-count versus normalized-float distinction, little-endian output, and integer clipping before narrowing must survive any future fused kernel. `wrap_pcm` already uses one compiled `struct.Struct` call and an unavoidable output-bytes concatenation; adding a codec decode/encode here would be wasteful. Its width/rate/field limits come from `wave.Error` and bounded struct fields; raw byte/frame alignment is intentionally not validated by this header-only function. That is a caller contract, not evidence that it validates arbitrary PCM.

For untrusted input, full-file `read` can allocate proportional to declared/present audio; bounded `blocks` reduces live memory but still parses native headers. SoundFile accepts more formats than stdlib wave, and 24-bit/FLOAT subtypes are tested capabilities. Replacing it with wave would remove those capabilities and change malformed-input outcomes. Existing tests already cover RIFF odd chunks, chunk boundaries, incomplete frames, write narrowing/large integers, stream channel mismatches and ownership of file handles.

Pack math is dtype item size, count, modulo/division for complete elements, endianness interpretation, and numeric coercion. The portable helpers restrict dtypes, use `memoryview.nbytes` for typed/multidimensional exporters, reject partial elements, and return fresh Python values. The unrestricted NumPy API deliberately supports NumPy dtypes. [NumPy's security guidance](https://numpy.org/doc/stable/reference/security.html) distinguishes untrusted data from untrusted dtype/shape/program control and calls out memory exhaustion. Keep network-controlled dtype strings behind an application's fixed schema or use the existing portable helper. [NumPy documents](https://numpy.org/doc/stable/reference/generated/numpy.frombuffer.html) that `frombuffer` aliases its source; a mandatory defensive copy would defeat the current zero-copy contract and add overhead. Use immutable/trusted buffer ownership at the boundary when the view must remain stable.

Time math is elapsed float subtraction/millisecond scaling; integer floor division of `time_ns`; exact `divmod(ms,1000)`; remainder-to-microsecond multiplication; and offset-aware `timedelta.total_seconds`/unit scaling. Retain exact integer conversion for negative epochs and far-calendar milliseconds. Converting epoch milliseconds through a float is a precision regression. `span` separately subtracts wall fields and offsets to handle a shared DST zone and avoid unnecessary UTC endpoint overflow at year limits. Calendar range, historical second-level offsets, invalid/naive policy, subclasses/custom tzinfo callbacks, truncation to microseconds, and protobuf Timestamp return identity constrain replacements. [The stdlib time documentation](https://docs.python.org/3.13/library/time.html) also makes platform clock/epoch behavior explicit.

Iterators perform count/index/step math and generic object equality rather than homogeneous numeric kernels. `ilen` uses C `count`/`zip`/`deque`; `windowed` uses tee/zip at unit stride and deque/islice otherwise; partition shares one predicate evaluation. [The itertools documentation](https://docs.python.org/3.13/library/itertools.html) warns tee can retain a growing lag and is not thread-safe. Adding locks or buffering limits would add cost/change behavior; require callers to consume partition branches together. `unique_everseen` retains all distinct keys, can require quadratic comparison work for unhashables, and executes user equality/hash code; replacing it with a set-only third-party helper loses its documented mixed-hashability semantics. Runs can materialize an arbitrarily long run; generic input limits belong at ingestion.

Containers expose backend classes directly: sortedcontainers sorted/rank operations over segmented Python lists and immutables persistent HAMT get/set/delete. Sorting is not an arithmetic kernel. Ordinary dict+sorted copies lose incremental ordering; MappingProxyType loses persistent-value semantics. Keys still execute user comparisons/hash functions; immutable mappings do not make mutable values immutable. No unmeasured adapter is justified by security or speed alone.

## Researched alternatives

- Retain NumPy kernels for existing arrays. Its [SIMD dispatch documentation](https://numpy.org/doc/stable/reference/simd/index.html) already describes CPU feature dispatch. These operations are codecs/conversions, not BLAS matrix multiplication, FFTs or large linear algebra; replacing a BLAS vendor is irrelevant to this code.
- [SoundFile `out`/buffer APIs](https://python-soundfile.readthedocs.io/en/latest/) can reuse caller-owned buffers, but silently reusing yielded `blocks` storage would change ownership/retention semantics. Consider only an explicit future `read_into` contract after end-to-end profiling; not a drop-in swap. Retain `Writer`'s open native handle across chunks.
- [SciPy wavfile.read](https://docs.scipy.org/doc/scipy/reference/generated/scipy.io.wavfile.read.html) exposes on-disk integer types (24-bit left-justified int32), different return ordering and mmap restrictions. Normalization/copy/adapter steps and a new dependency invalidate a zero-cost replacement claim. Unmeasured.
- [Hound](https://github.com/ruuda/hound) is a Rust WAV reader/writer and has fuzz infrastructure. It could underpin an ahead-of-time native WAV-only extension but requires a Python binding, buffer contract, parity, packaging and malformed-input evaluation. Memory-safe language is a rationale to investigate, not proof that an unmeasured new binding is faster or secure. Unmeasured.
- [NumExpr](https://numexpr.readthedocs.io/en/latest/vm2.html) documents VM setup penalties on small arrays; an extra evaluator and threadpool do not satisfy the no-overhead requirement. [Numba](https://numba.readthedocs.io/en/stable/user/jit.html) documents compilation on first execution or at decoration with explicit signatures. Runtime JIT and fixed-width arithmetic would introduce startup/semantic risks here. Both unmeasured and rejected as default swaps.
- [CuPy](https://docs.cupy.dev/en/stable/user_guide/basic.html) uses device allocations and host/device transfers. Existing public inputs/outputs are host bytes/NumPy arrays, so transparent GPU use introduces transfers, launches and synchronization. No relevant GPU-resident workload exists in these functions. Unmeasured; reject.
- [ciso8601](https://github.com/closeio/ciso8601) publishes faster ISO parsing benchmarks, but supports a different language, including midnight 24:00/lowercase z and only minute-level offset formats in its documented timezone grammar. Existing tests require historical second-level offsets such as `-04:56:02`. The package's own README cautions that it is not necessarily best since Python 3.11. Keep `datetime.fromisoformat`; no installed ciso8601 benchmark was claimed.
- [whenever's performance notes](https://whenever.readthedocs.io/en/latest/performance.html) explain a Rust extension and cached offsets; publisher benchmarks are not measurements of this facade's stdlib-to-whenever conversions. It is already used where DST disambiguation is required. Replacing timeutil's datetime-returning surface would add conversion and alter types. Keep both seams.
- [sortedcontainers' own comparison](https://grantjenks.com/docs/sortedcontainers/performance.html) warns that its synthetic benchmark performance varies and compares multiple C/C++ trees. A native tree does not universally beat a segmented list. No compatible measured replacement for all SortedList/SortedSet/SortedDict identities, APIs, comparison semantics and workloads was established.
- [immutables](https://github.com/MagicStack/immutables) describes structural sharing and HAMT logarithmic operations. It is already a C extension here and directly exposed. A copying dict or read-only view changes complexity/semantics. No replacement established.

## Conservative decision

No production backend swap is justified as universally faster, more secure, and overhead-free by the evidence available. Prioritize patched libsndfile build provenance and keep current APIs. The most concrete future speed change is eliminating round-trip float arithmetic for NumPy fallback PCM16-to-int16 decoding; its measured benefit is limited to that fallback. Keep float conversion and packing choices unchanged until representative workloads and the full supported version/platform matrix can establish no regressions.
