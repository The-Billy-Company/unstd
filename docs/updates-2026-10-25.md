## Build, layout and verification

- Python files are organized by technical concern with descriptive names and
  documented ownership. Public imports, native binary names and historical regex
  pickle identities are preserved. See the [architecture](architecture.md).
- Development and default runtime assurance use Python 3.14 while retaining
  the Python 3.12–3.14 compatibility matrices. Platform/runtime markers, dependency
  floors, TLS admission, compiler settings and macOS deployment floors remain
  part of release verification. See the [test guide](../tests/README.md).
- Native sources and vendor provenance live under `native/<package>/`. Wheels
  and source distributions are checked independently; optional compiler failures
  retain documented fallbacks, while strict release builds require their native
  payloads. See the [native guide](../native/README.md).
- Performance comparisons retain independent Linux/macOS and Python 3.13/3.14
  evidence, paired wall/CPU samples, source/binary hashes and failing results.
  Debug allocator, forced-GC, sanitizer and cancellation checks cover the affected
  native boundaries. See the [benchmark guide](../bench/README.md).

## What the speed claims establish

There is no package-wide or application-wide 100× guarantee. Rand's final
8,000-key fresh-batch count phase clears 100× in all nine paired wall/CPU samples
on macOS arm64 and a Linux arm64 VM; complete consumers remain much closer to
parity. Shared-branch JSON and primitive-buffer packing gains also depend on
their admitted input shapes and selected APIs. Unchanged controls, slower cases,
small-batch setup costs and hardware/storage limitations remain in the reports.
The [rand qualification](../bench/reports/rand/README.md) shows the distinction
between a qualified phase and complete workflow costs. Use the relevant package
guide and retained evidence before adopting a new API or extrapolating a result.
